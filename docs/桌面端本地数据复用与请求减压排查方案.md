# 桌面端本地数据复用与请求减压排查方案

> 版本：v1.0　日期：2026-08-21
> 范围：`desktop_client`（Electron + Vue3，本地库 SQLCipher）
> 定位：排查"哪些数据已存本地、哪些场景仍在无条件请求服务端"，给出分优先级的本地化复用方案。
> 关联文档：《桌面端本地存储方案》《桌面端本地存储实施计划》《桌面端消息同步减压优化方案》（消息历史的水位同步已在该文档落地，本文不重复）。

---

## 1. 结论摘要

桌面端本地存储（SQLite `workchat.db` + localStorage + 媒体文件缓存）已覆盖 **会话列表、消息历史、离线发送、媒体、好友/群列表缓存** 五大块，且"本地秒开 + 条件同步"机制已生效：**多数会话打开时历史消息 0 请求**。

当前仍在发生的可优化请求只有 4 类：

| # | 请求 | 触发时机 | 问题 | 优先级 |
|---|---|---|---|---|
| 1 | `GET /friends` + `GET /groups` | **每次进入通讯录页**（全量强刷） | localStorage 缓存已存在却被绕过 | P0 |
| 2 | `GET /version/latest` | 每次启动（延迟 2.5s） | 无 TTL，版本信息几乎不变 | P0（已实施 ✅） |
| 3 | `GET /groups/:g_uid` | 每个进程周期内首次打开每个群 | 只有内存缓存，重启即失效 | P1 |
| 4 | `GET /notifications` | 每次打开通知中心 | 无本地副本，离线不可见 | P1 |

登录链路上的 `GET /conversations?changed_since=` 是差量刷新（见 §2.3），数据量已很小，**建议保留**（它是多端一致性的兜底，见 §6）。

## 2. 现状盘点

### 2.1 已持久化在本地的数据（服务端不是必需来源）

| 载体 | 内容 | 写入时机 | 代码位置 |
|---|---|---|---|
| SQLite `conversations` | 会话列表全量：摘要/时间/未读/置顶/免打扰/草稿/标记未读/已读游标 `peer_read_seq`/同步水位 `last_synced_seq`/不落盘标记 | 登录差量刷新落库、WS 到达、发送、设置变更 | `electron/store/repos.js` |
| SQLite `messages` | 全部已同步消息 + 离线发送队列（`sync_state`）+ 语音已播标记 | 历史拉取、WS 推送、发送入队 | 同上 |
| SQLite `kv` | 备份时间、清理策略等元数据 | 设置页操作 | 同上 |
| localStorage `workchat:friends:cache` | 好友列表（含备注） | `/friends` 拉取成功后持久化 | `src/api/social.js` |
| localStorage `workchat:groups:cache` | 群列表 | `/groups` 拉取成功后持久化 | 同上 |
| localStorage（其他） | token、主题/字体、UI 偏好 | — | `src/api/token.js` 等 |
| 文件缓存 `files/{sha256}` | 图片/文件/语音媒体（`wcfile://` 换源） | 渲染时后台下载入库 | `electron/store/filecache.js` |

### 2.2 网络请求全景（触发时机与必要性）

| 请求 | 触发时机 | 本地可替代性 | 结论 |
|---|---|---|---|
| `POST /auth/login`、`/auth/refresh` | 登录/令牌续期 | 无 | 必须 |
| `GET /conversations?changed_since=` | 每次登录 `loadRealData` | 本地秒开已先行渲染；该请求只取变化部分 | 保留（多端兜底，§6） |
| `GET /conversations/:id/messages` | 打开会话/翻页 | **条件同步**：本地水位追平即 0 请求；翻页本地优先 | ✅ 已优化 |
| `GET /friends` | ① 通讯录页每次激活（强刷）② 缓存缺失时兜底 ③ 建群/邀请弹窗 | localStorage 缓存已持久化 | ⚠️ ①可优化（P0-2） |
| `GET /groups` | 同上 | 同上 | ⚠️ 同上 |
| `GET /groups/:g_uid` | 打开群会话/群设置（`groupMembersCache` 内存缓存） | 无持久层，重启失效 | ⚠️ P1-1 |
| `GET /notifications` | 通知中心打开（KeepAlive 首次挂载 + WS 事件触发刷新） | 无本地副本 | ⚠️ P1-2 |
| `GET /version/latest` | 每次启动 2.5s 后 + 手动检查 | 无缓存 | ⚠️ P0-1 |
| `GET /friends/requests` | 打开好友申请面板 | 未读红点已由登录响应带回，无轮询 | 保留 |
| `GET /conversations/search` | —（服务端接口） | 客户端搜索已全走 `localdb.messages.search` | ✅ 未被调用 |
| `POST /files/presign` | 上传媒体时 | 无 | 必须 |
| WS `/ws` | 登录后常驻 | 心跳 30s | 必须 |

### 2.3 已落地的本地优先机制（本次排查确认有效，不再重复建设）

1. **会话列表秒开**：`loadRealData` 先读本地库渲染，再差量刷新（`changed_since = 本地最新 last_msg_time - 1`），合并时按 id 去重。
2. **历史消息条件同步**：`loadConversationMessages` 中 `localMaxSeq >= syncSeq`（水位追平）时**直接返回、0 请求**；WS 每条到达消息实时推进水位（`persistWsIncoming → updateSyncSeq`），缺口自愈。
3. **向上翻页本地优先**：本地库有更早消息时不请求网络；`oldestSeq <= 1` 时直接判定无更多。
4. **聊天记录搜索本地化**：`SearchChatHistoryModal` 走 `localdb.messages.search`（服务端搜索接口已不调用）。
5. **好友/群缓存持久化**：localStorage 恢复 + 事件驱动失效（`friend.accepted`、建群/邀请/退群/踢人/`group.updated` 均 `clearCache`）。
6. **媒体文件缓存**：命中直接 `wcfile://` 换源，不重复下载；不落盘会话例外。
7. **离线发送队列**：`messages.sync_state='pending'` 行，重连后 `flushPendingQueue` 重发。
8. **会话增量事件**：`conversation.created` 事件本地直建会话项，不全量重载（含同 target 防重复合并）。

## 4. 优化方案

### P0：零服务端改动，立即可做

#### P0-1 版本检查 TTL 缓存（已实施 ✅ 2026-08-21）

- **实现**：`checkLatestVersion(currentVersion, { force })` 增加 24h TTL：检查结果（含"无版本记录"）写入 `localStorage workchat:update:cache`（`{ ts, latest }`），TTL 内自动检查直接复用不请求；手动"检查更新"传 `force: true` 不受限；网络失败不写缓存，下次启动照常重试。
- **涉及**：`src/api/version.js`、`SettingsWindow.vue`（手动路径传 force）；`App.vue` 启动自动检查默认走 TTL 无需改动。
- **收益**：每次启动 -1 请求（一天内重复启动收益更大）。
- **风险**：新版本发布最多延迟 24h 提示（手动检查可立即发现）；无数据一致性风险。

#### P0-2 通讯录页"缓存优先 + 条件后台刷新"

- **现状**：每次激活通讯录页 → 2 个全量请求。
- **改动**：
  1. 进入页面先用 `getCachedFriends()/getCachedGroups()` 立即渲染（缓存已由 localStorage 恢复）；
  2. 满足任一条件才发起后台 `list(true)` 强刷并静默更新视图：缓存为空、缓存写入时间超过 TTL（建议 5 分钟，时间戳随缓存一并持久化）、本次会话内收到过失效事件（`friend.accepted`/群事件已 `clearCache`，此时 `isFriendCacheLoaded()=false` 天然触发拉取）；
  3. 建群/邀请弹窗等需要最新数据的交互入口维持现有 `list(true)`，不受影响。
- **涉及**：`ContactsWindow.vue`、`social.js`（缓存增加写入时间戳字段）。
- **收益**：稳态下进入通讯录 0 请求（当前 2 请求）。
- **风险**：其他端加好友后，本端最坏延迟一个 TTL 周期才看到——但 WS `friend.accepted`/`conversation.created` 事件已会清缓存触发刷新，实际延迟≈实时。

### P1：新增本地表（SQLite schema v3+）

#### P1-1 群资料/成员持久缓存

- **新增表**：
  - `groups_cache(g_uid TEXT PRIMARY KEY, name, announcement, avatar, conv_id, invite_confirm, mute_all, saved, my_role, my_muted_until, fetched_at INTEGER)`
  - `group_members_cache(g_uid TEXT, uid TEXT, nickname, role, muted_until, saved, PRIMARY KEY(g_uid, uid))`
- **改动**：
  - `loadLiveGroupMembers`：先查本地表即时渲染 → 再按 `fetched_at` TTL（建议 10 分钟）或缓存缺失决定是否后台请求 `/groups/:gid`，响应回写本地表；
  - 现有失效钩子（`group.updated`、`group.left`、`group.kicked`、邀请/踢人成功后 `groupMembersCache.delete`）同步清本地表对应行。
- **收益**：进程重启后打开群 0 请求（当前每群 1 请求）；群资料离线可见。
- **风险**：成员列表短暂过期（TTL + 事件失效兜底）；禁言状态（`my_muted_until`）过期可能导致输入框状态滞后 ≤ TTL，打开会话即刷新可接受。

#### P1-2 通知持久化

- **新增表**：`notifications(id TEXT PRIMARY KEY, uid, type, title, summary, unread INTEGER, conv_id, g_uid, created_at)`。
- **改动**：`NotificationCenter` 打开时先渲染本地 → 再全量拉取对账落库（服务端暂无增量接口，见 P2-2）；`markRead/markAllRead/clear` 同步写本地；WS `notification:refresh` 事件维持。
- **收益**：通知中心秒开 + 离线可见。**请求数不变**（需 P2-2 才减请求），故定位为体验项。

#### P1-3 缓存键账户化（已实施 ✅ 2026-08-21）

- localStorage 缓存键改为 `workchat:{uid}:friends:cache` / `workchat:{uid}:groups:cache`，读取时按当前账户取键；旧键首次启动/登录时一次性迁移后删除（`social.js` `migrateLegacyCaches`）。
- 内存缓存增加归属账户校验（`cacheOwner`/`ownerOk`）：异常路径漏清理导致账户不匹配时按无缓存处理，防止串账户展示；登录成功后 `handleLoggedIn` 调 `reloadAccountCache` 重载新账户缓存。
- 彻底消除 P6 的串账户风险，不再依赖登出清理时序。

### P2：需要服务端配合

#### P2-1 通讯录增量接口

- `GET /friends?changed_since=` / `GET /groups?changed_since=`（按 `updated_at` 过滤，好友删除用软删或 tombstone 事件）；客户端合并逻辑复用会话列表差量模式（§2.3-1）。
- 前置：服务端 friends/groups 表补 `updated_at` 维护。收益：P0-2 的后台刷新从全量变差量。

#### P2-2 通知增量接口

- `GET /notifications?after_id=` 或按时间；客户端本地对账只补增量。收益：通知中心请求体从全量变差量（条数通常很少，收益有限，排在最后）。

## 5. 缓存失效矩阵（现有 + 规划）

| WS 事件 / 操作 | 失效对象 | 现状 |
|---|---|---|
| `friend.accepted` | 好友缓存 | ✅ `clearFriendCache` |
| 好友申请处理/删除好友 | 好友缓存 | ✅ `clearCache` |
| 建群/邀请入群成功 | 群缓存 | ✅ `clearCache` |
| `group.updated`（群名/公告/开关） | 群缓存 + 该群资料缓存 | ✅ 会话名同步 + `groupMembersCache.delete` |
| `group.left` / `group.kicked` | 该群会话/资料缓存 | ✅ 本地清理 |
| 踢人/设管理员/禁言成功 | 该群成员缓存 | ✅ 就地更新 |
| 版本检查成功（规划） | `update:last-check` TTL | P0-1 新增 |
| 通讯录缓存 TTL 到期（规划） | 后台强刷 | P0-2 新增 |
| 群资料 `fetched_at` 到期（规划） | 后台刷新群详情 | P1-1 新增 |

## 6. 风险与边界

1. **多端一致性**：本地缓存优先必然带来"他端变更延迟可见"。原则：**服务端为事实源，本地为投影**；WS 事件为主失效通道，TTL 为兜底。登录时的 `changed_since` 差量刷新是一致性兜底（纠正他端删除会话/改设置等事件未覆盖的场景），**不建议为省这 1 个小请求而跳过**。
2. **不落盘（敏感）会话**：所有本地化改造必须继续尊重 `no_persist`——主进程已在仓储层拦截（`repos.js` 的 `noPersistIds`），新增表/缓存沿用同一约束。
3. **离线数据陈旧提示**：离线渲染时维持现有"断线提示"交互，避免用户误把陈旧数据当最新。
4. **账户隔离**：本地库本身按账户分库（`accounts/{uid}/`），无串号风险；localStorage 缓存按 P1-3 补账户前缀。
5. **缓存膨胀**：新增表纳入现有存储治理（占用统计/清理/备份，`storage.js`），群资料/通知均为小表，无需额外清理策略。

## 一、项目现状总览

### 1.1 架构概况

| 子项目 | 技术栈 | 规模 | 状态 |
|---|---|---|---|
| `service/` | Go + Gin + MySQL（消息分表×4）+ Redis + 阿里云 OSS + WebSocket 网关 | ~8000 行 | 阶段五已落地（认证/消息/社交/管理后台/文件） |
| `desktop_client/` | Electron + Vue 3 + Vite | ~13000 行 | UI 完成，网络层已接真实后端 |
| `admin/` | Vue 3 + Vite | 较小 | 登录/看板/用户/群组管理可用 |

整体评价：**功能完成度高，工程质量不错**——后端分层清晰（router → 领域服务 → DAO）、有单测（mock 模式不依赖 DB）、有 6 个端到端测试脚本、消息链路有幂等去重和已读闭环设计。

但存在**两个可串联的越权漏洞、若干并发竞态、明显的性能隐患和工程化缺失**，需要按优先级逐步修复。

## 二、高优先级问题（安全与正确性）

### P0-1 越权读取任意会话历史【安全漏洞】

- **位置**：`service/internal/message/handler.go:45`、`service/internal/message/service.go:287`
- **问题**：`GetHistory` 从 token 解出 `uid` 后**从未校验该用户是否属于这个会话**，直接按 `convID` 查库返回消息。
- **影响**：任何登录用户拿到 conv_id 即可读取任意两人私聊的完整历史记录。
- **修复方案**：
  1. `GetHistory` 入口先查 `conversations` 表确认 `(owner_uid = uid AND target_id ∈ 会话)` 或用户是群成员；
  2. 同样校验 `RecallMessage`、`Send`（目标会话存在时的归属检查）。

```go
// 示例：GetHistory 增加归属校验
func (s *Service) GetHistory(uid, convID, beforeSeq int64, limit int) ([]*MessageDTO, error) {
    conv, err := s.store.GetConversationByID(convID)
    if err != nil || conv == nil {
        return nil, apperr.BadRequest("会话不存在")
    }
    // 单聊：必须是会话一方；群聊：必须是群成员
    if !s.isConversationMember(uid, conv) {
        return nil, apperr.Forbidden("无权访问该会话")
    }
    // ...原逻辑
}
```

### P0-2 搜索接口泄露全库消息【与 P0-1 串联】

- **位置**：`service/internal/message/service.go:388-406`
- **问题**：`Search` 调用 `store.SearchMessages(keyword, msgType, nil, limit)` 时 `convIDs` 传 `nil`，返回**所有用户会话**的命中消息（含 conv_id）。代码注释自己承认「这里返回所有命中，桌面端前端再按用户会话过滤」——把过滤责任交给前端等于没有过滤。
- **攻击链**：搜索任意关键词 → 拿到其他用户会话的消息内容和 conv_id → 利用 P0-1 拉取该会话完整历史。**两漏洞组合 = 全平台私聊可被任意用户读取。**
- **修复方案**：服务端先查出该用户的会话 id 列表，传入 `convIDs` 过滤（DAO 已支持该参数，只是上层没用）：

```go
func (s *Service) Search(uid int64, keyword string, msgType int8, limit int) ([]*SearchResultDTO, error) {
    // 先取该用户全部会话 id，限定搜索范围
    convs, err := s.store.ListConversations(uid)
    if err != nil { return nil, apperr.WrapInternal("获取会话失败", err) }
    convIDs := make([]int64, 0, len(convs))
    for _, c := range convs { convIDs = append(convIDs, c.ID) }
    if len(convIDs) == 0 { return []*SearchResultDTO{}, nil }
    results, err := s.store.SearchMessages(keyword, msgType, convIDs, limit)
    // ...
}
```

### P0-3 真实 OSS AccessKeySecret 明文在配置文件中

- **位置**：`service/configs/config.yaml:28`
- **问题**：真实的阿里云 `access_key_secret` 写在配置文件里，且项目当前不是 git 仓库，文件明文躺在源码目录。
- **修复方案**：
  1. **立即到阿里云控制台轮换该密钥**（即使未泄露也应视为已泄露）；
  2. 配置改为支持环境变量覆盖（如 `OSS_ACCESS_KEY_SECRET`），`config.yaml` 只留占位符。

### P0-4 JWT secret 无启动校验

- **位置**：`service/configs/config.yaml:34`、`service/cmd/server/main.go`
- **问题**：secret 默认值是占位符 `CHANGE_ME_TO_A_RANDOM_LONG_SECRET`，代码不检查是否已修改。用默认值启动时**任何人可伪造任意用户的 token**。
- **修复方案**：启动时校验，不合规直接拒绝启动：

```go
if len(cfg.JWT.Secret) < 32 || strings.Contains(cfg.JWT.Secret, "CHANGE_ME") {
    logger.Error("jwt secret 未配置或不安全，拒绝启动")
    os.Exit(1)
}
```

### P0-5 登录接口无防爆破

- **位置**：`service/internal/auth/service.go:140`（Login）
- **问题**：消息发送有 `rateLimiter`（每用户 1 秒 20 条），但**登录接口无任何限流**，可无限暴力尝试密码。
- **修复方案**：
  - 按「IP + 账号」双维度限流（复用已有的 `rateLimiter` 模式，如 IP 每分钟 10 次、账号每分钟 5 次）；
  - 连续失败 N 次锁定账号 15 分钟（Redis 计数）。

### P0-6 NextSeq 并发竞态导致消息发送失败

- **位置**：`service/internal/store/mysql/message.go:70-78`（NextSeq）、`message.go:48-67`（CreateMessage）
- **问题**：`NextSeq = MAX(seq)+1` 与 `INSERT` 是两条独立语句，无事务无重试。并发向同一会话发消息时两个请求拿到相同 seq，第二个撞 `uk_conv_seq` 唯一键报「保存消息失败」——**用户视角就是消息莫名发不出去**。
- **修复方案**（任选其一）：
  1. `Send` 捕获 duplicate key 错误自动重试 2~3 次（改动最小）；
  2. 改单语句：`INSERT INTO t (...) SELECT ?, COALESCE(MAX(seq),0)+1, ... FROM t WHERE conv_id = ?`（注意 MySQL 对同一表 INSERT...SELECT 的行为）；
  3. 用 Redis `INCR conv:seq:{convID}` 分配 seq（性能最好，需处理 Redis 故障降级）。

### P0-7 presence 键 90 秒过期但从不续期

- **位置**：`service/internal/gateway/hub.go:62`
- **问题**：`Add` 时写入 `presence:{uid}` TTL 90s，之后再无刷新。连接存活超过 90 秒后在线状态即失效——多节点路由会错判离线、把消息错误塞入离线队列；`IsOnline` 查询结果错误。
- **修复方案**：在 `readLoop` 收到心跳帧时顺手 `EXPIRE presence:{uid} 90`（本地无连接表的场景），或在 `handle(FrameHeartbeat)` 中续期。

### P0-8 前端断线期间发送的消息静默丢失

- **位置**：`desktop_client/src/api/ws.js:235-241`（sendFrame）、`ws.js:127`（clearPendingAcks）
- **问题**：
  - `sendFrame` 在连接非 OPEN 时**直接丢弃帧**，无任何提示；
  - 重连成功后 `clearPendingAcks()` 清空未确认队列，断线期间发出的消息即使进入队列也被清掉。
- **影响**：用户在弱网/断线瞬间发的消息无声消失，既没落库也没提示「发送失败」。
- **修复方案**：未连接时消息进入本地待发队列（持久化可选），重连成功后逐条重发——服务端已按 `msg_id` 幂等去重，重发不会产生重复消息。`clearPendingAcks` 改为「重发队列中的消息」而非清空。

## 三、中优先级问题（性能与可靠性）

### P1-1 群聊消息写放大严重（N+1 写）

- **位置**：`service/internal/message/service.go:229-242`
- **问题**：群聊每条消息要为**每个成员**执行 `GetOrCreateConversation` + `UpdateConversationLastMsg` + `UpdateConversationSyncedSeq` ≈ 3 次查询/成员，且全部同步阻塞在发送链路。**500 人群发一条消息 ≈ 1500 次 DB 查询。**
- **修复方案**：
  1. 批量化：按 `(owner_uid, target_id)` 主键批量 UPDATE（一条 SQL 用 `INSERT ... ON DUPLICATE KEY UPDATE` 或多值 IN）；
  2. 异步化：成员会话更新丢进 channel 由后台 worker 消费，发送链路只保证消息落库 + 推送；
  3. 未读数改「拉取时计算」：会话表不必实时维护 `last_synced_seq`，`ListConversations` 时以消息表最大 seq 为准（配合缓存）。

### P1-2 读路径 N+1

- **位置**：
  - `service/internal/message/service.go:408-425`（toDTO：每条消息 GetMessage + GetUserName = 2 次查询）
  - `service.go:303-347`（ListConversations：每会话 2 次 GetLastReadSeq）
- **问题**：拉 50 条历史消息 = 100+ 次查询；50 个会话的列表 = 100+ 次查询。
- **修复方案**：
  - `GetHistory` 直接用已查出的 `[]*mysql.Message` 组装 DTO（当前是查出列表后又逐条 `GetMessage` 回查，纯属浪费）；
  - `GetUserName` 加进程内 LRU 缓存（昵称变更频率低）；
  - `ListConversations` 用一条 JOIN 或 `WHERE (uid, conv_id) IN (...)` 批量取已读游标。

### P1-3 消息搜索是 4 张分表的全表 LIKE 扫描

- **位置**：`service/internal/store/mysql/message.go:196-244`
- **问题**：`content LIKE '%kw%'` 无法走索引，每词搜索扫 4 张消息全表。数据量增长后必然拖垮 DB。
- **修复方案**：
  - 短期：MySQL FULLTEXT 索引 + ngram 分词器（支持中文），`MATCH ... AGAINST` 替代 LIKE；
  - 中期：数据量大或需要全文搜索体验时，引入独立搜索引擎（MeilisSearch/Elasticsearch）。

### P1-4 HTTP 发送的消息不推送 + 节点 ID 硬编码

- **位置**：`service/cmd/server/main.go:109-113`、`main.go:117`
- **问题**：
  - `msgSvc` 的 `publish` 回调是**空实现**（只有注释），HTTP `/conversations` POST 发的消息接收方收不到实时推送；
  - 节点 ID 硬编码 `"node-1"`，未来多实例部署时所有节点同名，跨节点路由完全错乱。
- **修复方案**：publish 绑定到 `hub`（与 `pushFunc` 一致）；节点 ID 从配置读取或用 hostname/IP 自动生成。

### P1-5 网关可靠性细节

| 位置 | 问题 | 建议 |
|---|---|---|
| `gateway/server.go:125` | WS 首帧 auth 无读超时，恶意连接可永久挂死占资源（DoS 面） | auth 前 `SetReadDeadline(now+10s)` |
| `gateway/hub.go:138-155` | FlushOffline 先 RPop 再发送，发送失败消息即丢失；单次最多 200 条但无后续 flush 机制 | 改用 `LRANGE + LREM`（确认送达后再删）；滚动补发 |
| `gateway/hub.go:129-135` | 离线队列无 TTL 无上限，用户永不登录则无限膨胀 | `EXPIRE 7d` + 队列长度上限 |
| `gateway/hub.go:200-203` | 跨节点 route channel 满 256 直接丢帧；Redis Pub/Sub 本身不保证送达 | 扩容前改 Redis Stream（消费确认+持久化）；单机部署暂无影响 |
| `gateway/hub.go:81-84` | `IsOnline` 判断 bug：`err==nil` 恒为 true（key 不存在时 Exists 也返回 nil err）；目前是死代码 | 修复 `return n > 0` 或直接删除 |

### P1-6 令牌与 HTTP 细节

| 位置 | 问题 | 建议 |
|---|---|---|
| `auth/service.go:206` | Refresh 轮换后旧 refresh token 不拉黑，有效期内可重放 | 轮换时将旧 token jti 写入黑名单 |
| `server/middleware/cors.go` | 反射任意 Origin 且 `Allow-Credentials: true` | 生产环境改为 Origin 白名单 |
| `cmd/server/main.go:212` | 优雅退出只 Shutdown HTTP，不清理 WS 长连接 | 退出前 hub.Disconnect 全部连接，等待 readLoop 退出 |
| `admin/`（前端） | admin token 存 localStorage（XSS 可窃取） | 生产建议改 httpOnly cookie 或至少加短期过期 |

## 四、工程化与可维护性

### P2-1 没有 git 仓库（当前最大的工程风险）

- **现状**：项目不是 git 仓库、没有 `.gitignore`，且以下**构建产物/杂散文件混在源码目录**：
  - `desktop_client/release/win-unpacked/`（Electron 打包产物）
  - `desktop_client/dist/`、`admin/dist/`（构建产物）
  - `desktop_client/ardot_screenshots/`（截图）
  - 根目录 `login1.json`（杂散调试文件）
- **风险**：一次误删/磁盘故障即丢失全部代码历史；无法回滚、无法协作、无法上 CI。
- **修复方案**（半天内可完成）：
  1. `git init` + 编写 `.gitignore`（排除 `node_modules/`、`dist/`、`release/`、`bin/`、`*.local.yaml`、截图目录等）；
  2. 首次提交后立即推送远端（GitHub/Gitee/私有 GitLab）；
  3. 清理或迁出上述产物目录。

### P2-2 MainWindow.vue 4358 行巨型组件

- **位置**：`desktop_client/src/components/MainWindow.vue`
- **现状**：script 部分 1739 行、约 122 个函数/变量；template 约 695 行；style 约 1920 行。会话列表、消息渲染、已读管理、WS 事件分发、文件发送、群详情加载全部揉在一个文件。`SettingsWindow.vue`（2023 行）同样偏大。
- **影响**：任何前端迭代都在这个文件里进行，改动冲突面大、状态依赖难以追踪、加载即全量初始化。
- **拆分建议**（逻辑层用 composables、视图层用子组件）：

```
composables/
  useConversations.js   # 会话列表、未读数、切换逻辑
  useMessages.js        # 历史加载、乐观消息、分页
  useReadReceipt.js     # 已读游标、readCursorMap、restoreReadState
  useWsEvents.js        # onWsMessage/onWsRead/onWsSocial 分发
  useFileSend.js        # 图片/文件上传 + extra 组装
components/chat/
  ConversationList.vue  # 左侧会话列表
  MessageList.vue       # 消息流（配合虚拟滚动）
  MessageBubble.vue     # 单条消息气泡（含已读状态）
  ChatInput.vue         # 输入框 + 表情 + 发送
  GroupPanel.vue        # 群详情侧栏
```

- **注意**：拆分是纯重构，应分步进行，每步跑 `desktop_client/scripts/` 下的端到端测试回归。

### P2-3 缺前端基础设施

- **现状**：三个子项目均无 TypeScript、ESLint、Prettier、CI；`MainWindow` 内还残留 `HelloWorld.vue` 脚手架文件。
- **其他细节**：
  - `desktop_client/package.json` 中 `asar: false`——Electron 源码裸露且削弱完整性保护，发布版建议 `asar: true`；
  - `http.js:8` / `ws.js:7` 硬编码 `127.0.0.1:8080`，部署无法切换环境——改用 Vite 环境变量（`import.meta.env.VITE_API_BASE`）；
  - 桌面端无长列表虚拟滚动，消息多时 DOM 节点持续增长。
- **建议**：优先补 ESLint（防低级错误）+ 环境变量化（部署刚需）；TypeScript 可在新模块渐进引入。

### P2-4 文档与实现漂移

- **示例**：`CODEBUDDY.md:90` 写「readLoop 当前未真正实现超时踢线（仅回 pong）」，但 `gateway/server.go:150-167` 已实现（SetReadDeadline 60s 踢线）。这类漂移会误导后续修改。
- **建议**：以「文档即契约」为原则的项目，每次合入行为变更时同步更新 `CODEBUDDY.md` 与 `docs/` 对应章节；可在 CI 中加文档检查清单。

## 六、附录

### 6.1 分析中确认良好的部分（无需改动）

- **消息幂等去重**：`Send` 返回 `(dto, isNew)`，幂等重发静默处理，配合客户端 `msg_id` 重发机制设计完整；
- **单聊共享 conv_id**：`EnsureConversationID` 保证双方历史/已读同一会话，并有 `0005_conv_shared_id.sql` 迁移兜底；
- **已读游标模型**：会话级 `last_read_seq` 设计简洁，避免逐消息已读标记的写放大；
- **HTTP 层 401 刷新**：`http.js` 的 `refreshPromise` 并发去重实现正确；
- **Electron 安全基线**：`contextIsolation: true` + `nodeIntegration: false` + preload contextBridge 暴露最小面；
- **后端测试模式**：Service 定义最小 `Store` 接口 + 内存 mock，单测不依赖真实 DB，含可靠性测试与 bench。

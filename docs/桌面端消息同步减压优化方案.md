# 桌面端消息同步减压优化方案

> 背景：桌面端已接入本地存储（localdb，SQLite），但实际运行中仍频繁向后端拉取消息与会话列表，
> 本地缓存目前主要改善了"秒开体验"与"离线可用性"，**对服务器减压的贡献有限**。
> 本文梳理现状请求路径、定位根因，并给出按 ROI 排序的分阶段优化方案。

---

## 一、现状：HTTP 请求都发生在哪

以 `desktop_client/src/components/MainWindow.vue` 为准，当前会触发后端请求的路径：

| # | 触发时机 | 请求 | 是否必要 |
|---|---|---|---|
| 1 | 应用启动 / 登录后 `loadRealData()` | `GET /conversations` 全量 + `GET /friends` + `GET /groups`（有 localStorage 缓存，已加载不重发）+ 活跃会话历史 1 次 | 列表基线必要；历史这一次多数情况可省 |
| 2 | **每次切换会话** `selectConversation → loadConversationMessages` | 本地库先渲染，随后**必然发起** ≥1 次 `GET /conversations/:id/messages`（有本地数据时走 `after_seq` 增量；在线稳态下该请求**绝大多数返回空数组**） | **最大的浪费点** |
| 3 | WS `conversation.created` / `friend.accepted` 事件、邀请入群成功 | 又一次 `loadRealData()` → 全量 `GET /conversations` + 活跃会话历史重拉 | 事件本身已带足够信息，可增量处理 |
| 4 | 消息区向上翻页 | `GET ...messages?before_seq=` 每页 1 次 | 必要 |
| 5 | 发消息 / 已读回执 | 走 WS 帧，不占 HTTP | 已优化 |
| 6 | WS 实时收消息 | 不请求，直接落库渲染 | 已优化 |

补充两个关键事实：

- **服务端会话模型里已有 `last_synced_seq`（已同步最大 seq），但 `ConversationDTO` 没有下发**
  （`service/internal/message/service.go` 的 `ConversationDTO` 只有 id/type/target_id/last_msg/
  last_msg_time/unread/muted/peer_read_seq）。客户端因此**永远无法判断"本地是否已是最新"**，
  只能每次打开会话都"问一次"。
- **WS 推送的消息落库时不推进同步水位**：`persistWsIncoming` 只 upsert 消息行 + 更新会话摘要，
  从不调用 `localdb.conversations.updateSyncSeq`（该调用目前只存在于网络拉取成功后）。
  本地"同步游标"长期滞后，即使将来做条件同步也会误判"落后"而多发请求。

## 二、根因总结

1. **缺"新鲜度判据"**：客户端拿不到服务端每会话的最新 seq，无法跳过拉取（根因中的根因）。
2. **本地缓存只用于渲染，未参与请求决策**：秒开后仍无条件发请求，缓存与请求是两条互不通信的路径。
3. **事件处理粒度过粗**：一条"新会话建立"事件触发一次全量会话列表重载。
4. **同步水位维护不完整**：WS 入库路径不更新 sync_seq。

一句话：**本地存储解决的是"数据在不在本地"，减压需要解决的是"还要不要去问服务器"——后者目前没有任何机制。**

## 三、优化方案（按 ROI 排序）

### 阶段一：条件同步（改动小、收益最大，强烈建议先做）

**目标：在线稳态下，切换会话的历史请求从"每次 1 个"降为 0。**

1. 服务端：`ConversationDTO` 增加 `last_synced_seq` 字段（模型已有，直接透出，一行改动）。
2. 客户端 `persistWsIncoming`：WS 消息落库后，用消息 seq 推进
   `localdb.conversations.updateSyncSeq(convId, seq)`（补上缺失的水位维护）。
3. 客户端 `loadConversationMessages` 增加跳过逻辑：

   ```text
   本地有数据 且 localMaxSeq >= 该会话 last_synced_seq 且 非"不落盘"会话
       → 只渲染本地，不发任何网络请求
   否则
       → 走现有增量/全量拉取（拉取成功后更新水位，现有逻辑已有）
   ```

4. 会话列表落地该字段：`toConvItem` / localdb conversations 行保存 `sync_seq`，
   `loadRealData` 网络刷新时一并更新。

**安全性分析**（为什么按 seq 判断不会丢消息）：

- 新消息只会通过两条途径到达：WS 推送（实时落库并推进水位）或历史拉取。
  只要水位推进与落库同步，`本地最大 seq == 服务端最大 seq` 即内容一致。
- 撤回不产生新 seq，但撤回帧本身走 WS 推送（`persistWsIncoming` 已处理 status=1 落库）。
  极端情况（长时间离线且离线队列被 LTrim 截断）可能漏掉撤回帧——此时本地水位落后，
  条件同步会自动触发拉取补齐，方向安全（宁可多拉，不会漏）。
- "不落盘"会话、本地无数据的会话、`last_synced_seq` 缺失（旧数据）一律走网络拉取，兜底不破。

**预期收益**（以日均切换 50 次会话、90% 时间在线且无漏推为例）：
历史请求 ≈ 50 次/天 → ≈ 5 次/天（仅落后/新会话/无本地数据场景）。

### 阶段二：会话列表增量化

**目标：社交事件不再触发全量列表重载。**

1. `conversation.created` / `friend.accepted` 事件处理改为增量：
   事件体已携带 `conv_id` / `g_uid` / `type`，直接本地构造一条会话项（名称取自联系人缓存，
   摘要留空待首条消息 bump）+ 落 localdb；仅在信息不足时回退全量 `loadRealData()`。
   （当前 `openPlaceholderConversation` 已有占位会话机制，可复用同一套合并逻辑。）
2. 邀请入群成功后：只失效该群成员缓存 + 增量刷新对应会话项，不再全量重载。
3. （可选，服务端配合）`GET /conversations?changed_since=<unixts>`：
   客户端传本地 `max(last_msg_time)`，服务端 `WHERE owner_uid=? AND last_msg_time > ?`
   （`idx_owner_last (owner_uid, last_msg_time)` 索引已存在，零新增成本），
   启动/重连时的列表刷新从"全量"变"差量"。

**预期收益**：每次好友通过/建群/入群邀请省去 1 次全量列表 + 1 次历史重拉；
会话较多时列表接口传输量显著下降。

### 阶段三：可选增强

| 项 | 说明 | 建议 |
|---|---|---|
| 会话列表 ETag/304 | 服务端对列表算指纹，客户端带 `If-None-Match`，未变化返回 304 | 只省带宽与序列化，服务端查询照跑；收益一般，可选 |
| 增量拉取页大小自适应 | 落后 seq 差 ≤100 单请求；>100 才翻页（现状已如此，保持 10 页上限） | 保持现状 |
| WS 重连后条件补拉 | 重连时对"活跃会话 + 离线期间有新消息的会话"按阶段一逻辑条件拉取，替代盲目重拉 | 依赖阶段一，顺手做 |
| 搜索本地先行 | 先查 localdb 命中即返回，不命中再走服务端 | 体验优化，不减压，可选 |
| 媒体文件 | wcfile:// 内容哈希缓存已生效 | 无需改动 |

## 四、实施清单（阶段一 + 阶段二）

服务端（`service/`）：
- [x] `internal/message/service.go`：`ConversationDTO` 增加 `LastSyncedSeq int64 \`json:"last_synced_seq"\``，`ListConversations` 组装时填充
- [x] （阶段二）`GET /conversations` 支持 `changed_since` 查询参数（返回该时间后变化的会话，含空会话保证完整）

桌面端（`desktop_client/src/components/MainWindow.vue`）：
- [x] `toConvItem`：映射 `syncSeq: Number(c.last_synced_seq) || 0`；localdb conversations upsert 时持久化
- [x] `persistWsIncoming`：落库后 `localdb.conversations.updateSyncSeq(convIdStr, Number(msg.seq))`（status=1 撤回帧同样推进，保持水位单调）
- [x] `loadConversationMessages`：首页非翻页分支增加“本地已最新则跳过网络请求”判断
- [x] （额外修复）`electron/store/repos.js` 会话 upsert 的 `last_synced_seq` 改为 MAX 单调语义，
      防止不带水位字段的部分行 upsert（如 WS 摘要更新）把本地水位回退为 0
- [x] `onWsSocial`：`conversation.created` 改增量插入（新增 `insertConvFromEvent`，事件体携带真实 conv_id 字符串），删除无脑 `loadRealData()`；服务端好友接受/建群事件同步改为下发真实 conv_id
- [x] 邀请成功回调：去掉全量重载（邀请不改变自己的会话列表）；`onCustomFriendAdded` 仅 WS 断开时兜底全量
- [x] `loadRealData` 差量刷新：本地有数据时按 `changed_since` 只拉变化会话，未变化会话保留本地项（含未读/水位），同 target 占位会话被真实会话替换

## 五、验证方法

1. DevTools → Network：切换 10 个"在线且无新消息"的会话，`/messages` 请求数应为 0（改造前为 10）。
2. 服务端 `server.log`：统计 `/conversations/:id/messages` 的 QPS 前后对比。
3. 回归用例：
   - 离线 10 分钟（断网期间对方发 3 条）→ 恢复网络 → 打开会话应自动补齐 3 条；
   - 对方撤回一条 → 在线实时收到撤回帧；离线超时后打开会话 → 条件拉取补齐撤回状态；
   - "不落盘"会话打开 → 仍走网络；
   - 新账号换机登录（本地无数据）→ 首屏正常走网络拉取。
4. 已有 E2E 脚本回归：`scripts/test_conv_list.mjs`、`scripts/test_messages_refresh.mjs`、
   `scripts/test_unread_cycle.mjs`。

## 六、风险与取舍

- **一致性模型从"每次问服务器"变为"按水位信任本地"**：与微信/QQ 的本地缓存模型一致；
  水位落后时自动补拉，方向安全。唯一的弱一致窗口是"撤回帧丢失且水位恰好不落后"的极端组合，
  概率极低，且可通过"手动刷新会话"兜底。
- **多端场景**：水位是"本端同步状态"，与其他端无关，天然无冲突。
- **旧本地数据**：没有 `sync_seq` 的历史行按 0 处理 → 首次打开心照常拉取一次并建立水位，自然过渡。
